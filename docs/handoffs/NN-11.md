## Ownership and numerical behavior

The input is float32 with concrete rank at least two, shaped `[N,C,...]`.
Scale, bias, mean, and variance are required float32 rank-one tensors shaped
`[C]`. Epsilon is explicit, finite, and nonnegative; there are no schema
defaults. The operation evaluates
`scale * (x - mean) / sqrt(variance + epsilon) + bias` in float32 per channel.
The square root uses the existing float32 standard-math wrapper. Rank-two
feature, NCHW spatial, and higher-rank inputs use the same channel rule.

All input/parameter types, ranks, shapes, epsilon, destination shape/type, and
storage identities are checked before writes. Inputs and all statistics remain
unchanged. Destination aliases are rejected, including shallow copies and
empty tensors. Repeated read-only parameter tensors are allowed. Returned
errors preserve destination values and metadata. Outputs are caller-owned and
survive later calls. Shared immutable inputs/statistics can be read concurrently
with disjoint destinations. No mutable global state or retained scratch exists.

Empty N, C, or spatial dimensions are valid after full validation. Empty calls
skip unused spatial products, so a concrete zero can make otherwise enormous
unused iteration spaces unnecessary. Nonempty calls reuse `checkedProduct`
before host conversion; the validated payload length bounds channel/spatial
indices. Private `validateNormalizationParameter` performs named float32 and
exact `[C]` checks. Shared `validateTensorType`, `validateDestination`, and
`shapesEqual` retain their existing contracts.

No momentum, training flag, statistics update, layer, optimizer parameter,
gradient, or backward cache is constructed. Negative variance plus epsilon
follows sqrt domain behavior without clamping. Zero divisors and nonfinite
values follow the literal floating expression, producing NaNs/infinities as
appropriate. NaN payloads and floating bitwise agreement across backends are
not promised. Finite fixture comparisons use `atol=rtol=1e-5`, NaNs compare by
classification, and infinity signs compare exactly.

## References and compatibility limits

Thirty-one original fixtures use independent NumPy broadcasting rather than
the Go loop's explicit channel indexing. Tools: Python 3.9.6, ONNX 1.16.2,
NumPy 1.26.4, protobuf 4.25.3, and ONNX Runtime 1.19.2. Development environment:
`/private/tmp/neuralnetwork-onnx-reference/bin/python`. Ordinary Go tests read
checked-in JSON offline. No Python, ONNX runtime, or module dependency is added
to library builds. Fixture SHA-256:
`4788058268769cb709bfc099aa137e5417d9dd26c5391c19d4de090fa0e6b8bc`.

Models use IR 8, imported standard-domain opset 13, BatchNormalization-9,
and one output. Actual evaluator/ORT shapes and float32 bits are retained.
ONNX Runtime's CPU provider uses one intra/inter-op thread and disabled graph
optimizations. It agrees with 30 expected results; the sole difference is a
zero-variance/zero-epsilon domain case. With input `[-1,0,1]`, scale 1, bias
and mean 0, and variance/epsilon 0, the literal expression gives
`[-Inf,NaN,+Inf]`, while ORT produces three NaNs. This is an explicit numerical
limit rather than a general ORT-equivalence claim.

The ONNX 1.16.2 schema-9 evaluator agrees on eight cases and differs on 23.
Its wrapper applies momentum to supplied means/variances even for inference
with one output. The stored-statistics contract is preserved instead. For
input `[3,5]` shaped `[2,1]`, scale 2, bias 0.5, mean 1, variance 4, and
epsilon 0, both the independent formula and ORT give `[2.5,4.5]`; the evaluator
gives approximately `[2.2675757,4.3470764]` using default momentum 0.9.
Explicit momentum-attribute fixtures also retain the evaluator's outputs;
momentum is not a library parameter and has no effect on the kernel.

Fixtures cover nondefault/zero epsilon, nontrivial learned statistics, multiple
batches/channels, ranks two through six, empty values, negative variance,
nonfinite inputs/parameters, and negative-zero epsilon. The fixture README
links exact primary reference/schema sources. These selected cases do not
establish general ONNX compatibility or a runtime schema/profile policy.
